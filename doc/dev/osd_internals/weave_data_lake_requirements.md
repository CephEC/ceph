# Weave 后台聚合 EC 需求分析：按时间分区的日志数据湖

> 文档性质：目标场景、当前实现边界与评估要求。
> 当前采用“逻辑删除 + 每日定时或手动稀疏卷清理”，不要求新增应用生命周期接口。单成员覆盖写脱离仍是后续设计方向，不属于本次实现。
> 文件大小、保留期等示例是工作负载假设，不是已有业务测量结果。

当前设计尚未闭环。D1 已补充持久化转换提交协议，见 [D1 专项记录](weave_d1_recovery.md)。仍未完成的 PG split、版本／启停准入、候选再发现和失败收敛，统一记录在 [Weave 问题台账](weave_issue_register.md)。下文的目标语义不能替代这些尚未完成的机制。

## 1. 项目定位

面向以 Ceph 为存储后端、按时间分区、历史数据基本不可变的日志数据湖，通过后台 EC 对象聚合优化存储访问，并将逻辑删除与物理空间回收分离。

项目不是通用的前台聚合存储，也不以频繁随机修改、频繁行级更新的数据库工作负载为优化目标。

核心取舍：**先复用普通 EC 和既有后台聚合流程，以可配置、低频的稀疏卷拆解控制空间占用，不引入生命周期识别系统或 Volume 之间的直接合并。**

## 2. 典型业务场景

### 2.1 数据来源和消费方式

业务数据包括网站访问日志、App 埋点和追加式业务事件。数据通过 Flink 或批量导入任务写入 Parquet，再由 Spark、Trino 等计算引擎按日期读取、过滤和统计。

典型任务包括每日流量统计、用户行为分析和离线报表计算。

```text
日志、埋点、业务事件
        |
        v
Flink / 批量导入任务生成 Parquet
        |
        v
Ceph 存储
        |
        v
Spark / Trino 按日期读取、过滤、统计
```

该流程描述目标业务架构，不代表当前分支已完成查询引擎接入、RGW 路径验证或 SQL 下推。

### 2.2 目标工作负载

| 维度 | 场景假设与边界 |
| --- | --- |
| 数据组织 | 按表、日期分区组织；补数或重算时可以区分不同代的数据 |
| 写入模式 | 微批导入和追加为主，写入集中在分区开放阶段 |
| 稳定性 | 分区封闭后，文件基本不再变化 |
| 读取模式 | 对历史分区重复执行读取、过滤和批量扫描 |
| 删除模式 | 主要由保留期到达、旧分区淘汰或旧一代数据失效触发 |
| 零散修改 | 允许偶发纠错、覆盖和单对象删除，但它们不是主要负载 |
| 文件大小 | 优先研究微批写入和大量分区形成的小文件，例如 1–16 MiB 的 Parquet 文件 |
| 保留期 | 可以用 30 天作为实验示例；实际期限由业务确定 |

不假设所有 Parquet 文件都是小文件，也不强求已经很大的文件参加聚合。示例 Parquet 文件大小不能直接当作底层 RADOS 对象大小，二者的对应关系取决于接入路径。

### 2.3 生命周期

| 阶段 | 访问特征 | 目标存储行为 |
| --- | --- | --- |
| 当前分区持续写入 | 微批导入，文件不断增加 | 普通 EC 写入，不在前台选组或聚合 |
| 分区封闭并稳定 | 写入基本结束，后续以读取为主 | 后台选择合适对象进行聚合 |
| 保留期内分析 | 重复读取和扫描，偶尔补数或纠错 | 通过逻辑成员映射访问；非删除修改沿用整卷恢复普通 EC 的路径 |
| 分区可以淘汰 | 应用确认旧数据不再需要 | 持久化成员失效状态 |
| 物理空间释放 | 空卷或达到存活比例阈值的稀疏卷 | 每日定时或手动清理；空卷直接删除，稀疏卷先恢复存活成员 |

分区何时可以删除仍由应用决定，并通过普通对象删除表达。当前聚合层不识别表、日期或保留期，也不要求应用提供分区封闭状态；候选资格沿用大小、同 PG 和静默时间规则。

## 3. 要解决的问题

### 3.1 降低底层对象访问开销

微批写入与多表、多分区组合可能形成大量较小对象。本项目研究后台聚合能否降低这些对象在普通 EC 布局下的分片访问、数据汇集和相关存储开销。

收益需要与普通 EC 基线对比验证，不能仅凭聚合后的物理对象数量减少就推断查询一定更快。

### 3.2 避免单个成员删除导致整卷重写

删除一个成员不应要求读取、清零或重编码整个 Volume。删除状态提交后即可应答，失效槽位的物理空间稍后统一回收。

覆盖写与逻辑删除需要区分：当前非删除修改仍先把有效成员恢复为普通 EC，再执行原生操作。单成员覆盖写脱离不在这次清理机制的实现范围内。

### 3.3 控制残留空间与搬运成本

同一 Volume 的成员可能在不同时间失效。全部失效时可以直接整卷删除；仍有存活成员时，通过阈值决定是否值得搬运。

日志分区批量淘汰是有利的业务特征，而不是实现必须识别的生命周期分组条件。收益和代价需要通过实际删除轨迹测量。

## 4. 聚合需求

### 4.1 前台边界

- 未聚合对象走普通 EC 写入、提交和应答流程。
- 前台不选择聚合组，不等待组满，不拼装聚合 Volume。
- 候选登记属于后台聚合的接入点，不应成为凑组完成与否决定写入应答的机制。
- 聚合后的成员访问需要必要的映射适配；这不等于前台聚合，也不能据此声称前台完全没有额外路径。
- 后台任务会竞争存储资源，因此仍需评估它对前台延迟的影响，不能承诺零性能干扰。

### 4.2 分组边界

当前候选分组沿用已有后台规则：

1. 不跨 PG 聚合，不改变池的 EC 参数和固定 stripe unit。
2. 选择大小接近、满足最小大小和静默时间的普通 EC 对象。
3. 受 Volume 大小、填充比例与后台并发限制约束。
4. 凑不齐一组时保持普通 EC，不阻塞前台。
5. 不从对象名猜测业务生命周期，不声称已经实现按表或分区分组。

当前成员元数据不保存原生 `truncate_seq` / `truncate_size`。任一字段非零的对象保持普通 EC，不进入聚合；发布前再次检查，避免读取已应用的截断历史时返回错误的短数据。

按生命周期分组可以作为独立的后续对照策略，但不是当前使用本功能的前提。

候选索引按当前最小对象大小和 `floor(max_volume_size / k / unit) * unit` 槽位上限准入，每 PG 最多保留 4096 个对象；后台聚合暂停期间同样遵守上限。配置收紧时淘汰不再合格的已有候选，新增候选在容量已满时不再登记。被尺寸或容量排除的对象在下一次已提交修改时重新判断资格；放宽配置不会全 PG 扫描旧对象。已有合格候选在重新启用后台聚合和 PG 进入 clean 时获得扫描唤醒。单次扫描跳过 busy 对象继续凑组，不放松原生对象锁。

PG reset 会清空尚未处理的候选，重启或角色变化后的初始化只恢复 Volume Catalog，不补扫普通对象。因此当前没有“停止写入的历史冷对象最终都会被发现并聚合”的保证；有界再发现是未完成工作，见问题台账 D4。

### 4.3 发布和访问语义

聚合是物理布局变化，不是逻辑文件合并。客户端看到的对象身份、内容、长度、属性、版本和列举结果应保持符合原有接口语义。

后台选择对象后，需要防止并发修改导致发布过期内容。新 Volume 的数据提交、成员映射发布和源对象回收之间必须有明确、可恢复的顺序。

本文不指定具体事务实现，也不假设多个对象位于同一 PG 就使多步操作自动具有原子性。

## 5. 覆盖写与逻辑删除需求

### 5.1 不可变 Volume 与可变成员状态

已发布 Volume 的数据布局保持不变，通过持久化成员映射表达删除：

```text
物理数据仍然保留：
    Volume V = [A, B, C旧, D]

逻辑状态已经变化：
    A、B、D -> V 中的原位置
    C      -> 已删除，可以重新创建同名普通 EC 对象
```

成员失效不等于把槽位数据置零。旧数据和校验数据在正确回收之前仍需保留，不能仅凭逻辑删除就对 EC 数据直接打洞。

### 5.2 当前操作行为

| 操作 | 数据处理 | 完成条件 |
| --- | --- | --- |
| 单对象删除，或以 DELETE 结束的受支持断言/读取组合 | 在普通 EC 事务内更新 Volume 的 `_volume_meta`，不改写成员数据 | 删除元数据可靠提交后返回，不等待清理 |
| 同卷并发删除 | 对共享成员元数据执行互斥的读改写，保留原生请求去重 | 不能覆盖另一个已提交删除 |
| 完整或部分覆盖成员 | 先将 Volume 中仍有效的成员恢复为普通 EC，再重放原生修改 | 保持原操作语义；当前仍有整卷读和存活成员写放大 |
| 不支持的组合操作 | 沿用恢复普通 EC 后执行的路径，不拆散原子操作 | 原生事务决定成功或失败 |
| 分区补数或重算 | 由应用生成新内容并决定旧对象何时可以删除 | 不新增业务生命周期或版本发布接口 |

上述元数据删除捷径仅适用于没有快照历史、且请求没有快照上下文的池。存在快照历史时，删除和其他修改先恢复原生对象，再执行原生 copy-on-write。快照 READ／STAT／属性访问同样先恢复包含该 head 的 Volume，由原生 snapset／clone 路径解析具体快照；快照身份不会被当成一个不存在的 Catalog head。

新 Volume 使用当前元数据布局（v1，`ENCODE_START(1,1)`），保存每个源对象的原生 `snapset.seq`。恢复对象时沿用该序号，不能套用恢复时的最新池快照上下文，否则会把对象误判成在快照之后才创建。物理 Volume 自身的写入／回收不产生新的池快照克隆。元数据只接受这一种布局：其他 `struct_v` 的属性按损坏拒绝，没有兼容分支，不再有“以物理 Volume 的快照序号兜底”的降级行为。现有数据不支持回退到不认这一布局的 OSD。

转换期间需要协调受影响逻辑对象的请求；不能把“由后台执行”误解为发起修改的请求完全不需要等待。

成员脱离后继续走普通 EC，只有重新满足稳定性条件才考虑再次聚合，避免写入和聚合之间反复转换。

### 5.3 逻辑状态的持久性

- 映射切换和删除状态不能只保存在内存中。
- 已确认的删除不能在重启或重载 Volume 元数据后复活。
- 同名对象重建需要区分对象代际，旧成员失效或旧卷清理不能误伤新对象。
- 新对象尚未可靠提交前，不能撤掉唯一有效的旧数据访问路径。
- 逻辑删除不承诺物理擦除或密码学意义上的不可恢复删除。

Catalog 的持久化来源仍是 Volume 对象的 `_volume_meta`。BlueStore 使用独立 RocksDB 前缀 `V`，以原 onode key 为键保存元数据原始字节的副本，并与 onode 在同一 KV 事务中维护；属性更新、删除、克隆和重命名均同步处理。Catalog 加载只遍历当前 collection/PG 的 Volume 索引范围，不再逐 PG 扫描普通对象。空卷仍保留索引，直到物理 Volume 被删除。

D1 将 Volume 数据与有效映射的共同提交作为接管原生成员的提交点。源版本与快照资格在提交前验证，成员预留保持到交接结束。反向物化必须先持久化全部成员，再确认 Volume 删除，最后撤销内存映射；取消或超时不能推翻已经提交的事实。恢复依据磁盘重新加载，重复归属直接报错，不按加载顺序选取版本。详细故障窗口与验证方法见 [D1 专项记录](weave_d1_recovery.md)。

索引加载同时返回实际 head 对象身份；恢复临时对象、快照和回滚代际不作为已发布 Volume。控制器只接受私有 namespace 中、实际对象与元数据声明身份一致的记录。普通用户的同名 `volume_meta` 属性不能发布成员映射；真实 Volume 的元数据损坏或身份不匹配时返回错误，不按空 Catalog 继续服务。

Catalog 加载成功后才开放 primary 的逻辑访问。本地仍有缺失对象或恢复事务尚未应用时，读、写和列举等待元数据恢复；加载失败保持错误状态并允许后续重试，不能将未恢复成员误判为不存在。原生请求重排队时先恢复逻辑对象和原始操作，再进行权限检查与映射解析。

Weave 只在 BlueStore EC PG 上启用；MemStore 等不支持 Volume 索引的后端保持原生 EC 请求路径，默认加载器仍返回 `-EOPNOTSUPP`。列举的 xattr 过滤从当前成员所在 Volume 读取属性，但过滤器接收原来的逻辑对象身份；陈旧副本待恢复的物理源对象删除，不覆盖有效 Catalog 中的逻辑成员。

复合 data-class CALL 按子操作顺序执行。尚未完成的 CALL 是解释屏障，前置异步 READ 的结果必须先通过原生错误处理；非 FAILOK 失败不会执行后续 CALL／READ／STAT。逻辑 STAT 在实际执行到对应子操作时才编码输出，预处理不提前填充结果。执行 shard 的 class 加载错误按实际错误码返回，缺失方法返回 `-EOPNOTSUPP`。OpenCV thumbnail 的畸形参数、非有限数、零／负尺寸和放大请求返回 `-EINVAL`。

`V` 索引从对象创建起与 onode 属性同步维护，挂载时直接使用已持久化的索引，不扫描 `O` 重建，也不使用完成标记。不提供未维护索引的旧存储迁移或旧二进制回退写入后的兼容路径；`_volume_meta` 格式和副本直读接口保持不变。

## 6. 物理空间回收机制

### 6.1 一次清理的处理顺序

1. 枚举本 OSD 当前 primary、active、clean 的 EC PG 的 Volume 元数据。
2. 优先删除没有有效成员的空卷，不读取其 payload。
3. 对满足 `有效成员数 × 100 <= 数据槽位数 k × 阈值` 的非空卷，读取该卷并只将存活成员写回普通 EC。
4. 存活副本可靠提交后撤下旧映射、删除旧卷；保留对象内容、大小、mtime、xattrs 和逻辑版本。
5. 恢复的普通对象重新登记为候选，从恢复时重新计算静默期，交给既有聚合流程重新凑组。

不直接把多个 Volume 合成新 Volume，不为删除清零槽位，也不重新发布已删除成员。同名对象重建不能被旧卷清理覆盖。

“全量扫描”指 Volume 元数据枚举，不是读取所有卷的数据。未命中阈值的卷不读取 payload；当前被选中的稀疏卷仍采用整卷读取，仅写出有效成员。

### 6.2 配置与手动命令

| 配置 | 默认值 | 语义 |
| --- | --- | --- |
| `osd_weave_cleanup_time` | 空字符串 | 严格的 `HH:MM`，按 UTC 每日触发；空值关闭自动清理，不禁用手动命令 |
| `osd_weave_cleanup_live_percent` | `50` | 有效成员占原始数据槽位的百分比，范围 `0–100`，边界包含；不是有效字节百分比 |
| `osd_weave_max_concurrent` | `1` | 清理与普通后台聚合共用的 OSD 并发上限；`0` 暂停任务准入 |

```sh
ceph config set osd osd_weave_cleanup_time 02:00
ceph config set osd osd_weave_cleanup_live_percent 50

# 异步执行一次，使用目标 OSD 当前的阈值。
ceph tell osd.0 weave cleanup
ceph tell 'osd.*' weave cleanup

# 关闭每日触发，仍可手动执行。
ceph config set osd osd_weave_cleanup_time ""
```

`02:00` 是 UTC 时间，例如北京时间 10:00。启动或修改配置后只安排下一个未来时点，不补跑已经错过的时间；运行期间时钟跳变也不会逐日补跑。

手动和定时入口共用一次清理流程，每个 OSD 不重复启动同时运行的清理轮次。命令返回 `accepted` 或 `already_running`，不是等待释放空间完成；没有符合条件的 PG 或 Volume 时也可以接受并立即结束。每轮使用启动时的阈值。

阈值 `0` 只回收空卷，`100` 连满卷也会拆解；后者可能制造无收益的转换。默认 `50` 是可调整的起点，不是未经测量的最优策略。

### 6.3 资源与语义边界

- 沿用每 OSD 一个后台 worker、每 PG 一个转换任务和现有并发限制，不新增 cron 或专用清理线程。
- `osd_weave_background_enabled=false` 只关闭普通候选扫描，清理仍可运行。重新启用会唤醒已有候选，不要求再发生一次前台写入。
- 非空卷要先写出存活对象，再删除旧卷，因此必须预留空间；这不是满盘时保证能够完成的原地压实。
- 在途访问、成员删除和转换通过 PG 锁、对象锁及逻辑对象预留协调；延迟或取消后的请求恢复原始对象身份和输入后重新解析映射。
- 打包期间普通 head 只读请求在发布前访问原生对象、发布后访问 Volume；共享读取可与打包并行，来源删除重试不阻塞新读。写、删、快照及需要物化的操作仍遵守转换屏障；物化不适用这项读放行。
- 已发布卷的删除状态通过原生 EC 提交持久化。D1 已引入明确的转换提交点与恢复裁决，并用故障边界矩阵验证；PG split/resharding 仍是独立边界，不能由转换验证推导出全故障保证。

仍未完成的边界包括：PG split 尚无成员与 Volume 的迁移协调，也没有 pool 层强制阻止；已有格式的解释依赖 OSD 本地开关，尚无版本准入或关闭前排空保护。必要物化还共用后台租约，对永久写入／删卷错误没有终止策略。详见问题台账 D2、D3、D5；它们是未完成的实现机制，不只是尚未运行的测试。

需要分别测量逻辑删除延迟、物理释放延迟、暂时空间峰值和搬运字节数。

## 7. 大数据接入与能力边界

### 7.1 Parquet 文件不一定等于 RADOS 对象

如果通过 RGW/S3 访问 Ceph，一个 Parquet 文件可能对应多个底层 RADOS 对象。聚合层看到的对象大小、名称和生命周期信息，未必与上层文件直接对应。

因此需要确认：

- 实际接入路径，以及上层文件与底层对象的映射关系；
- 不依赖生命周期提示时，实际对象删除轨迹会产生怎样的稀疏度；
- 对象删除和底层回收的实际时序；
- Parquet 扫描能否获得完整、可解析的文件视图。

不能仅凭底层对象名推断 Hive 风格分区，也不能直接对一个任意文件片段承诺完整 Parquet 扫描。

### 7.2 不替代逻辑小文件合并

底层 Volume 聚合不会自动减少 Spark、Trino 等引擎看到的逻辑文件数量，因此不能直接解决查询规划、文件枚举和逐文件打开等全部小文件问题。

本项目与 Spark 或 Iceberg 的逻辑文件合并不是同一层次的优化。

### 7.3 不默认提供完整 SQL 下推

项目中的 Parquet 扫描方向可以与这个场景对应，但查询引擎是否调用存储侧计算、支持哪些算子、如何保持结果语义，都需要明确接入和验证。

存储侧扫描收益应与单纯布局聚合收益分开评估，不能把已有数据类调用接口等同于完成 Spark/Trino SQL 下推。

## 8. 非目标

- 不恢复或引入前台凑组、写缓存式聚合流程。
- 不以频繁随机覆盖、频繁行级更新的通用数据库负载为主要优化对象；必要修改仍需保持正确语义。
- 不改变池的 `k/m`、固定 stripe unit 或 PG 归属来适配单个聚合组。
- 不引入应用生命周期 API、日期猜测或跨 Volume 直接合并。
- 不把每次删除后的立即压实作为默认要求。
- 不承诺底层聚合自动减少逻辑文件数、替代数仓文件合并或完成查询引擎下推。
- 不因参考 f4 而引入外部密钥数据库，也不把逻辑删除当作安全擦除。

## 9. 评估方法与验收关注点

### 9.1 对照策略

在相同硬件、池参数、数据内容和业务轨迹下，对比：

1. 普通 EC，不进行对象聚合。
2. 同 PG 按大小聚合，配合每日或手动阈值清理。
3. 若后续实现生命周期分组，再将其作为独立对照，不作为当前能力。

普通 EC 到聚合 EC 不改变 `k/m`，因此不能把 f4 从多副本转 EC 的冗余率下降当成本项目的预期收益。填充、元数据和访问效率的变化需分别测量。

### 9.2 工作负载必须覆盖对象的完整生命周期

评估不能只有顺序写入和随机读取，还应包括：

- 微批导入和分区封闭；
- 历史分区重复读取与扫描；
- 少量零散覆盖、删除和补数；
- 整分区或旧一代数据淘汰；
- 无法及时凑组、稀疏卷积累以及空间压力下的后台清理。

### 9.3 关键指标

| 指标 | 关注问题 |
| --- | --- |
| 聚合覆盖率 | 大小、静默时间和 PG 边界下，有多少对象和字节能够聚合 |
| 读取与扫描效率 | 吞吐、延迟、分片访问和网络数据量是否改善 |
| 前台写入延迟 | 后台资源竞争与成员转换对尾延迟的影响 |
| 直接整卷回收比例 | 多少失效空间能在不搬运存活数据的情况下释放 |
| 残留失效空间 | 逻辑删除后仍占用多少物理空间、持续多久 |
| 回收搬运成本 | 清理过程的读写字节数相对于最终净释放物理字节数的比例 |
| 后台总开销 | 聚合与清理消耗的 I/O、网络、CPU 和任务积压 |
| 物理释放延迟 | 从应用允许淘汰到实际释放空间的时间 |

物理空间和回收成本的统计需要注明 EC 冗余、填充及元数据开销的计量口径。净释放空间不为正时，应单独报告无净收益的清理，不能给出误导性的比值。

### 9.4 正确性验收关注点

- 未聚合对象不因等待凑组而延迟完成写入。
- 聚合不改变逻辑对象内容及原有接口语义。
- 普通成员删除不以重写其他成员为前提；覆盖写的整卷恢复成本单独统计。
- 未修改成员在聚合、成员脱离和回收期间保持可正确访问。
- 删除和覆盖已确认后，故障恢复不能重新暴露旧成员内容。
- 空间回收不能提前删除仍被有效成员、在途访问或必要保留引用使用的数据。

性能收益和可接受的空间占用比例，需要在代表性负载上确定；本文不预设未经测量的提升幅度。

## 10. 需要确认的业务与接入信息

| 待确认项 | 影响 |
| --- | --- |
| 真实文件大小及底层对象大小分布 | 聚合覆盖率、填充开销与扫描粒度 |
| 微批大小、分区数量及各 PG 内的对象数量 | 同 PG 大小分组是否容易凑齐 |
| 分区何时封闭，迟到数据和补数如何处理 | 静默期设置与转换频率 |
| 保留期是否统一，是否存在额外保留引用 | 整卷回收机会与安全释放时点 |
| 删除字节中有多少来自整分区淘汰 | 简单回收策略是否适合实际业务 |
| 零散覆盖和删除的比例、时间分布 | 成员脱离成本与长期空洞占用 |
| RGW/S3 或其他实际接入路径 | 对象映射、删除时序与接口兼容性 |
| 查询引擎与存储侧扫描的集成方式 | 哪些计算收益可以纳入评估 |

## 11. f4 的参考价值与不能照搬的部分

参考文献：[f4: Facebook’s Warm BLOB Storage System，OSDI 2014](https://www.usenix.org/system/files/conference/osdi14/osdi14-paper-muralidhar.pdf)。

- §5.3：编码后的数据和索引保持只读，删除通过外部每 BLOB 密钥的移除实现。值得借鉴的是数据与可变状态分离，而不是照搬密钥系统。
- §6.5：论文当时的 f4 不回收已删除 BLOB 的空间，测得该部分占用为 6.8%。这是其特定低删除率负载下的取舍，不是本项目可以直接采用的空间预算。
- §7：把删除跟踪移出只读存储层改善了系统简单性与稳定性。
- f4 的 BLOB 不支持修改；本项目的单成员脱离是为 Ceph 可变对象语义提出的设计方向，不是 f4 原文已经解决的覆盖写方案。

本项目借鉴其“根据工作负载限定设计”的方法：保留普通 EC 语义，以持久化逻辑删除和低频可配置清理处理失效空间，再通过真实负载衡量是否需要更复杂的生命周期分组或单成员覆盖写脱离。
